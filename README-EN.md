**LoopWarden** is a high-performance Ethernet Loop Detector (L2 Loop Detector). It monitors the network in real-time to alert on physical loops and broadcast storms within milliseconds, drastically reducing diagnosis time (MTTR).

## 🚀 Key Features

LoopWarden runs **13 concurrent detection engines**. Each one looks for a specific "signature" of failure or threat on the network, providing complete Layer 2 visibility:

### 1. ActiveProbe (Deterministic Active Injection) ⚡
*The network's "Sonar". The only way to be certain.*

*   **🔬 Mechanics:** LoopWarden generates and injects a broadcast Ethernet frame (`FF:FF:FF:FF:FF:FF`) with a configurable EtherType `0xFFFF`. The payload contains a magic signature, the interface identity, and a **Network Domain** (Domain ID).
*   **🛡️ Detection Logic (Topology Awareness):**
    *   **Self-Loop (Hard Loop):** If the probe returns with the **same source MAC**, it's a physical loop on the port itself. (Critical Alert).
    *   **Legitimate Neighbor:** If the probe comes from another MAC but has the **same Domain** (e.g., both are "VLAN10"), it's considered another LoopWarden sensor coexisting on the same network. (Silence).
    *   **Cross-Domain Loop:** If the probe comes from another MAC with a **Different Domain** (e.g., receiving "VLAN10" on my "VLAN20" interface), there's a critical physical bridge between two isolated networks. (Critical Alert).
*   **💡 Differential Value:** Unlike passive methods, ActiveProbe doesn't generate false positives in environments with multiple sensors. It allows monitoring the same VLAN from different points without sensors "attacking" each other.
*   **🎯 What it detects:**
    *   ✅ **Physical Loops:** Patch cable connected back-to-back.
    *   ✅ **VLAN Leaking:** Crossed cables between racks from different departments.
    *   ✅ **STP Failures:** Switches where Spanning Tree has failed or is slow to converge.


### 2. EtherFuse (Passive Payload Analysis) 🧬
*Detection of "bounces" through fast hash fingerprinting.*

*   **🔬 Mechanics:** Passively inspects incoming Broadcast/Multicast traffic. Calculates an ultra-fast hash (FNV-1a) of the frame content (payload). Stores these hashes in a circular buffer.
*   **🛡️ Detection Logic:** If the system observes the same hash `N` times within a millisecond time window, it means the frame is "orbiting" the network infinitely.
*   **💡 Differential Value:** Capable of detecting **remote** loops. Even if the loop isn't on your local switch, you'll receive the shockwave of duplicated packets.
*   **🎯 What it detects:**
    *   ✅ **Remote Loops (Soft Loops):** Loops on unmanaged switches downstream.
    *   ✅ **Signal Bounces:** Duplicated packets due to configuration errors on redundant links.

### 3. MacStorm (Per-Host Speed and Volumetrics) 🌪️
*Isolating the source of the problem.*

*   **🔬 Mechanics:** Maintains a real-time state table tracking Packets Per Second (PPS) generated by each unique source MAC address.
*   **🛡️ Detection Logic:** Applies a logical Rate Limit. If an individual MAC exceeds the defined threshold, it's marked as a hostile host.
*   **💡 Differential Value:** It doesn't just tell you "there's a problem", it tells you **who** is the problem (MAC Address), enabling precise blocking action.
*   **🎯 What it detects:**
    *   ✅ **Faulty Network Cards (Jabbering NICs):** Damaged hardware sending garbage to the network.
    *   ✅ **Volumetric DoS Attacks:** Bandwidth saturation attempts.
    *   ✅ **Anomalous Traffic:** Uncontrolled P2P clients or software errors.

### 4. FlapGuard (L2 Topology Consistency) 🦇
*Detection of VLAN leaks and port instability.*

*   **🔬 Mechanics:** Creates a dynamic map of the `MAC Address <-> VLAN ID` relationship.
*   **🛡️ Detection Logic:** Monitors if the same MAC address appears in different VLANs at very short time intervals (Flapping).
*   **💡 Differential Value:** A classic symptom of misconfigurations that STP doesn't always block.
*   **🎯 What it detects:**
    *   ✅ **VLAN Leaking:** Misconfigured switches allowing tagged traffic to escape.
    *   ✅ **Crossed Cabling:** Accidental physical bridges between two different VLANs.
    *   ✅ **Logical Loops:** Circular network routes between broadcast domains.

### 5. ArpWatchdog (Control Plane Protection) 🐶
*Early warning system and pattern analysis.*

*   **🔬 Mechanics:** Performs Deep Packet Inspection (DPI) of ARP packets, analyzing volume, source MAC, and destination IPs (Min/Max Range).
*   **🛡️ Detection Logic:** Analyzes whether ARP traffic corresponds to normal behavior, an attack, or a physical failure.
*   **💡 Differential Value:** Intelligently distinguishes between a loop and a hacker based on destination IP dispersion.
*   **🎯 What it detects:**
    *   ✅ **Network Scans (Discovery):** Sequential IP sweeps (`nmap`, `arp-scan`). The log will show `SUBNET SCANNING`.
    *   ✅ **Network Loops:** The same ARP packet repeating infinitely toward a single IP. The log will show `SINGLE TARGET ATTACK`.
    *   ✅ **Virus/Malware:** Lateral propagation of worms trying to discover victims in the subnet.
    *   ✅ **Gratuitous ARP Flood:** GARP packet flooding (Sender IP == Target IP) indicative of IP conflicts, VRRP/HSRP flapping, or ARP Poisoning attacks.

### 6. DhcpHunter (Rogue DHCP Hunter) 🦈
*Security against Man-in-the-Middle.*

*   **🔬 Mechanics:** Analyzes UDP packets (Port 67/68) verifying the source MAC and IP against a whitelist (`trusted_macs`).
*   **🛡️ Detection Logic:** If an unknown server offers an IP to a client, it's immediately marked as Rogue.
*   **🎯 What it detects:**
    *   ✅ **Home Routers:** Users connecting TP-Link/D-Link through the LAN port.
    *   ✅ **MITM Attacks:** Gateway spoofing through DHCP Spoofing.
    *   ✅ **Configuration Errors:** Servers with accidentally activated DHCP roles.

### 7. FlowPanic (802.3x Pause Detection) ⏸️
*Physical health and DoS monitoring.*

*   **🔬 Mechanics:** Tracks Ethernet control frames (`0x8808`) with OpCode `PAUSE`.
*   **🛡️ Detection Logic:** A flood of these frames indicates a device is collapsing or trying to stop the network.
*   **🎯 What it detects:**
    *   ✅ **Critical Hardware Failure:** NICs or Switches about to die from full buffers.
    *   ✅ **L2 DoS Attacks:** Pause frame flooding to freeze traffic without saturating bandwidth.

### 8. RaGuard (IPv6 Router Advertisement Guard) 📡
*IPv6 infrastructure protection.*

*   **🔬 Mechanics:** Inspects ICMPv6 packets looking for "Router Advertisement" messages.
*   **🛡️ Detection Logic:** Only allows RAs from the MACs of authorized Core routers.
*   **🎯 What it detects:**
    *   ✅ **Rogue IPv6 Gateways:** Devices (mobile/Windows) announcing themselves as routers and hijacking traffic.
    *   ✅ **Shadow IT:** Unauthorized parallel IPv6 networks created by IoT devices.

### 9. McastPolicer (Multicast Storm Control) 👻
*Cloning and streaming management.*

*   **🔬 Mechanics:** Differentiates and measures Multicast traffic (IPv4 `01:00:5E...` / IPv6 `33:33...`) separating it from Broadcast.
*   **🛡️ Detection Logic:** Applies specific rate limits, allowing distinction between a video class and a catastrophic loop.
*   **🎯 What it detects:**
    *   ✅ **Cloning Storms:** Misconfigured software like FOG/Clonezilla.
    *   ✅ **Video Leaks:** IP cameras or IPTV flooding access ports.
    

### 10. BcastRatio (Broadcast vs Total Ratio) 📊
*Early warning of network degradation.*

*   **🔬 Mechanics:** Atomically counts all received packets and those that are pure broadcast (`FF:FF:FF:FF:FF:FF`). Every second it calculates the broadcast percentage over the total.
*   **🛡️ Detection Logic:** If the ratio exceeds the configured threshold (`max_ratio`, default 70%) with a minimum sample (`min_sample_size`, default 100 pkts/s), it generates a degradation alert.
*   **💡 Differential Value:** Detects the **formation** of a storm before it becomes catastrophic. An 80% broadcast ratio indicates the network is on the brink of collapse even if the absolute PPS hasn't triggered other engines.
*   **🎯 What it detects:**
    *   ✅ **Incipient Storms:** Slow loops that don't yet generate enough PPS for EtherFuse but are already degrading the network.
    *   ✅ **Gradual Degradation:** Networks where broadcast grows slowly due to accumulation of misconfigured devices.

### 11. VlanLeak (Inter-VLAN Leak Detector) ☣️
*Network segment isolation surveillance.*

*   **🔬 Mechanics:** Tracks which VLANs each source MAC visits. Maintains a `MAC → {VLAN → last seen}` map and compares it against a list of **prohibited VLAN pairs** defined in the configuration.
*   **🛡️ Detection Logic:** If the same MAC appears in two VLANs that are marked as prohibited (e.g., Server VLAN 10 and Guest VLAN 200), an immediate segmentation leak alert is generated.
*   **💡 Differential Value:** While *FlapGuard* detects rapid VLAN changes (flapping), *VlanLeak* detects traffic that should **never cross** between segments, regardless of speed. Ideal for compliance audits (PCI-DSS, ISO 27001).
*   **🎯 What it detects:**
    *   ✅ **Segmentation Leaks:** Management VLAN traffic appearing in the guest VLAN.
    *   ✅ **Trunk Errors:** Trunk ports allowing VLANs they shouldn't.
    *   ✅ **Policy Violations:** Devices accessing segments prohibited by network policy.

### 12. MetaEngine (Multi-Engine Correlator) 🧠
*High-confidence confirmation through cross-correlation.*

*   **🔬 Mechanics:** Subscribes to the Notifier's alert stream. Each time an engine generates an alert, the MetaEngine records the event with its timestamp. Maintains a configurable sliding time window.
*   **🛡️ Detection Logic:** If **2 or more distinct engines** fire alerts within the same time window (default: 2 seconds), the MetaEngine elevates severity to `CONFIRMED LOOP - MULTI-SIGNAL DETECTION`. Example: if *ActiveProbe* detects a self-loop and *EtherFuse* detects repeated payloads simultaneously, confidence is maximum.
*   **💡 Differential Value:** Drastically reduces false positives. An individual alert could be noise, but two independent engines confirming the same event in the same time window is near-absolute certainty.
*   **🎯 What it detects:**
    *   ✅ **Confirmed Loops:** Correlation between active and passive detection.
    *   ✅ **Coordinated Attacks:** Multiple simultaneous anomalies (Rogue DHCP + MAC Flood).
    *   ✅ **Cascade Failures:** Infrastructure problems triggering multiple alarms.

### 13. Multi-Stack Granular Tuning 🎛️
*Hierarchical per-interface configuration.*

*   **🔬 Mechanics:** LoopWarden allows defining a global security policy and applying **specific exceptions** (Overrides) per interface.
*   **🛡️ Logic:**
    *   **Global:** Defines strict rules for the entire network (e.g., "No one can scan IPs").
    *   **Local:** Relaxes or hardens rules for specific ports (e.g., "The `vlan_guest` interface can make more ARP requests, but `mgmt` has zero tolerance").
*   **💡 Differential Value:** Allows deploying a single LoopWarden instance to monitor heterogeneous environments (Servers, IoT, Users, Wi-Fi) without generating false positives in noisy zones.

#### 14. Neighbor Discovery (Topology Awareness) 🗺️
*Physical context for each alert.*

*   **🔬 Mechanics:** A passive engine that decodes **LLDP** (Link Layer Discovery Protocol) and **CDP** (Cisco Discovery Protocol) frames in real-time. Extracts the System Name, Port, Chassis ID, and **Management IP Address** from the neighbor switch.
*   **🛡️ Logic:** Doesn't generate alerts by itself. Its function is to maintain a "Neighbor Map" in memory (`TopologyStore`). When another engine (e.g., *EtherFuse*) detects a loop, it queries this map to tell you not only *that* there's a loop, but **exactly which switch and physical port the sensor is connected to**.
*   **💡 Differential Value:** Transforms a generic alert ("Loop on eth0") into a precise work order ("Loop on eth0, connected to Switch-Core-01, Port Gi1/0/48, IP 10.10.1.1").

### 📊 Telemetry and Observability (Prometheus & API)

LoopWarden is designed under the "Glass Box" philosophy: total internal and external visibility without the need for third-party agents. The system exposes a lightweight HTTP server (default `:9090`) with two key endpoints for daily operation.

#### 1. Performance Metrics (`/metrics`)
Natively compatible endpoint with **Prometheus**. Allows visualizing network and detection engine health in real-time through Grafana.

*   **Layer 2 Forensics:** Granular traffic breakdown by protocol (ARP, IPv4, IPv6, VLAN Tagged, LLDP, Control Frames) and transmission type (Broadcast vs Multicast). Identifies which exact protocol is saturating the link.
*   **Kernel Health (Zero-Blindness):** Directly monitors network driver drop counters (`rx_dropped`). If the Kernel drops packets due to buffer saturation before LoopWarden can read them, the `loopwarden_socket_drops_total` metric will reveal it, ensuring no operational blind spots exist.
*   **Threat Trends:** Specific counters for each detection engine (`loopwarden_engine_hits_total`). Allows correlating CPU spikes on switches with historically detected ARP storms or physical loops.
*   **Latency Profiling:** Nanosecond-precision histograms (`loopwarden_processing_ns`) measuring how long each packet takes to traverse the engine stack, validating "Fast-Path" performance.

**Quick Verification:**
```bash
curl http://localhost:9090/metrics
```

#### 2. Live Topology API (`/topology`)
Thanks to the *Neighbor Discovery* engine, LoopWarden maintains a real-time "neighborhood map" by listening to LLDP and CDP frames. This endpoint returns a **JSON** snapshot of the current physical connection state.

Ideal for **Automation Scripts**, Dynamic Inventory systems, or simply to know "What the heck is this cable connected to?" without going to the rack.

### 🔔 Intelligent Notifications (Smart Silence & Dampening)

During a broadcast storm, a network can generate millions of events per second. A naive alerting system would crash your email server or block your Slack API. LoopWarden implements **Configurable Operational Hygiene**:

*   **Global Dampening:** Configurable in the `[alerts.dampening]` section. If the system detects an alert flood exceeding the defined threshold (default: 60 alerts/minute), it automatically activates "Panic Mode". It silences global notifications for the stipulated time (`mute_duration`, default: 60s) and sends a single consolidated summary at the end.
*   **Granular Cooldowns:** Each algorithm has configurable cooldown times (`alert_cooldown`). For example, you can configure *ActiveProbe* to alert every 5 seconds, while forcing *FlapGuard* to remain silent for 5 minutes after detecting an unstable host, adapting noise to event criticality.
*   **Integrations:** JSON Webhooks (Slack, Discord, Mattermost, Google Chat, Rocket.Chat), **Telegram Bots**, Syslog (RFC 3164), and SMTP (Email).

## 🎚️ Tuning and Calibration Guide

LoopWarden comes configured by default for medium-sized environments (Offices/SMBs). In high-density environments like **Educational Centers, Universities, or Data Centers**, thresholds need to be adjusted to differentiate legitimate traffic from anomalies.

Use this guide to adjust `config.toml` according to your network's behavior.

### Configuration Strategy (Global vs Local)

Before adjusting numbers, decide your deployment strategy to keep the `config.toml` file maintainable.

1.  **The 80/20 Rule:** Configure **Global** values thinking about your critical servers or core infrastructure (where you want absolute silence and fast detection). This will cover 80% of your ports.
2.  **The "Noise Pit":** Identify interfaces connecting to User networks, Guest Wi-Fi, or Labs. These networks are noisy by nature (mDNS, Windows Broadcasts, Consoles).
    *   **Don't raise the global limit** to accommodate users, or you'll leave servers unprotected.
    *   **Use Overrides:** Create a specific entry for that noisy interface:
        ```toml
        [algorithms.arp_watch.overrides.guest_vlan]
        max_pps = 2000 # Allow discovery scans on Wi-Fi
        ```
3.  **ActiveProbe on Core vs Access:**
    *   On **Core (10Gbps)** links, use a slow interval (e.g., `5000ms`) to avoid saturating logs or graphs.
    *   On **Access** links, use a fast interval (e.g., `override interval_ms = 500`) to detect the loop as soon as the user incorrectly connects the cable.

### 🧬 EtherFuse (Bounce Detection)
*Detects identical duplicated packets.*

*   **`history_size` (Hash Memory)**
    *   **📈 WHEN TO INCREASE (e.g., 8192 or 16384):**
        *   **Symptom:** Slow loops or "Soft Loops" in very large networks that aren't detected.
        *   **Cause:** In networks with high traffic, the circular buffer overwrites too quickly before the duplicated packet returns. Increasing this consumes more RAM but "remembers" packets for longer.
    *   **📉 WHEN TO DECREASE (e.g., 1024):**
        *   **Symptom:** Deployments on very limited hardware (embedded routers with little RAM).
*   **`alert_threshold` (Repetition Sensitivity)**
    *   **📈 WHEN TO INCREASE (e.g., 200-500):**
        *   **Symptom:** Intermittent alerts without network failure.
        *   **Cause:** Classroom software (teacher control), mDNS (Apple/Chromecast), or P2P applications on the LAN legitimately sending the same payload many times.
    *   **📉 WHEN TO DECREASE (e.g., 20-50):**
        *   **Symptom:** The network becomes slow before LoopWarden alerts.
        *   **Cause:** Distant loops with high attenuation or packet loss.
*   **`storm_pps_limit` (Global Panic)**
    *   **📈 WHEN TO INCREASE (e.g., 30000):**
        *   **Symptom:** "GLOBAL STORM" alerts during school or work day start.
        *   **Cause:** Hundreds of devices connecting and broadcasting at once.

### ⚡ ActiveProbe (Active Probe)
*Traffic injection for physical confirmation.*

*   **`interval_ms` (Probe Frequency)**
    *   **📈 WHEN TO INCREASE (e.g., 2000 ms):**
        *   **Symptom:** High CPU usage on the LoopWarden server or desire to minimize noise in Wireshark captures.
    *   **📉 WHEN TO DECREASE (e.g., 200-500 ms):**
        *   **Symptom:** Protection of critical equipment where a 1-second loop is unacceptable. Near-instant detection.

### 🌪️ MacStorm (Per-Host Limit)
*Prevents a single network card from saturating the medium.*

*   **`max_pps_per_mac` (Unicast Speed)**
    *   **📈 WHEN TO INCREASE (e.g., 5000-8000):**
        *   **Symptom:** Alerts about Backup Servers, NAS, camera NVRs, or image cloning servers.
        *   **Cause:** Massive file transfers or legitimate high-density traffic.
    *   **📉 WHEN TO DECREASE (e.g., 1000):**
        *   **Symptom:** Strict need for traffic control on guest or IoT networks.

### 🦇 FlapGuard (VLAN Dancing)
*Detects rapid port/VLAN changes.*

*   **`threshold` (Movements)**
    *   **📈 WHEN TO INCREASE (e.g., 20):**
        *   **Symptom:** Alerts about WiFi users (Roaming) or Servers with LACP/Bonding.
        *   **Cause:** The client jumps between APs quickly or the server load-balances between physical interfaces.
    *   **📉 WHEN TO DECREASE (e.g., 2-3):**
        *   **Symptom:** Static environments (Datacenter) where a cable should never move. Immediate detection of cabling errors.
*   **`window` (Time Window)**
    *   **"1s" (Default):** Standard.
    *   **"5s" (Long):** Useful for detecting "slow flapping" in complex Wi-Fi networks where the client roams indecisively.

### 🐶 ArpWatchdog (ARP Storm)
*Monitors address resolution requests.*

*   **`max_pps` (Global Requests)**
    *   **📈 WHEN TO INCREASE (e.g., 2000):**
        *   **Symptom:** False positives first thing in the morning.
        *   **Cause:** Massive classroom/office boot-up (Boot Storm).
    *   **📉 WHEN TO DECREASE (e.g., 100):**
        *   **Symptom:** Small or critical security networks.
*   **Scan Mode (`scan_mode_pps`)**
    *   ArpWatchdog now distinguishes normal traffic from a scan. If a device touches more than `scan_ip_threshold` (10) different IPs, a stricter limit is applied (`scan_mode_pps`, default 100) to quickly detect malware infections (`nmap`, worms).

### 🦈 DhcpHunter and 📡 RaGuard (Security)
*Infrastructure Whitelists.*

*   **`trusted_macs` / `trusted_cidrs`**
    *   **Action:** These aren't numeric thresholds. Here you must **EXPLICITLY** add the MACs of your legitimate DHCP servers and Routers. Anything not on this list that acts as a server will generate an immediate alert.

### ⏸️ FlowPanic (Pause Frames)
*Hardware Health and DoS.*

*   **`max_pause_pps`**
    *   **📈 WHEN TO INCREASE (e.g., 200):**
        *   **Symptom:** Old switches or heavily saturated links using Flow Control aggressively.
    *   **📉 WHEN TO DECREASE (e.g., 10):**
        *   **Symptom:** You want to know immediately if a network card or cable is defective and negotiating poorly.

### 👻 McastPolicer (Multicast Storm)
*Video and cloning traffic control.*

*   **`max_pps`**
    *   **📈 WHEN TO INCREASE (e.g., 20000+):**
        *   **Symptom:** Alerts when using cloning software (FOG, Clonezilla) or HD Videoconferencing.
        *   **Cause:** Multicast traffic is the foundation of these tools.
    *   **📉 WHEN TO DECREASE (e.g., 1000):**
        *   **Symptom:** WiFi network collapses but wired doesn't.
        *   **Cause:** Multicast traffic floods the airspace (transmitted at base rate). Lowering this protects WiFi.

### 📊 BcastRatio (Broadcast Ratio)
*Early proportional degradation warning.*

*   **`max_ratio` (Maximum Percentage)**
    *   **📈 WHEN TO INCREASE (e.g., 0.85):**
        *   **Symptom:** Frequent alerts on networks with many Windows devices (NetBIOS) or IoT generating legitimate broadcast.
    *   **📉 WHEN TO DECREASE (e.g., 0.5):**
        *   **Symptom:** Critical networks (Datacenter, SCADA) where any significant broadcast is abnormal.
*   **`min_sample_size` (Minimum Sample)**
    *   **📈 WHEN TO INCREASE (e.g., 500):**
        *   **Symptom:** False positives on low-traffic interfaces (e.g., management link with 50 pps where 40 are ARP).
    *   **📉 WHEN TO DECREASE (e.g., 50):**
        *   **Symptom:** Low-speed networks where 100 pps is already significant.

### ☣️ VlanLeak (Inter-VLAN Leaks)
*Network segmentation surveillance.*

*   **`prohibited_pairs` (Prohibited Pairs)**
    *   **Action:** Explicitly define which VLAN pairs should **never** share traffic. Example: `[[10, 200]]` will prohibit a MAC seen on VLAN 10 from appearing on VLAN 200.
    *   **Planning:** Review your network segmentation matrix. Typical pairs to prohibit: Management vs Guest, Servers vs IoT, Production vs Development.

### 🧠 MetaEngine (Correlation)
*Confirmation sensitivity tuning.*

*   **`threshold` (Minimum Engines)**
    *   **📈 WHEN TO INCREASE (e.g., 3-4):**
        *   **Symptom:** Correlation alerts too frequent. You want maximum certainty before escalating.
    *   **📉 WHEN TO DECREASE (e.g., 2):**
        *   **Symptom:** Default. Two independent engines confirming is already high confidence.
*   **`window` (Correlation Window)**
    *   **"2s" (Default):** Standard for loops that trigger alerts almost instantly.
    *   **"5s" (Wide):** Useful if engines have long cooldowns and alerts arrive with delay.

## 🚨 Incident Response Playbook

Quick action guide for network operators (NOC) facing critical LoopWarden alerts:

| Alert Received | Probable Cause | Recommended Action |
| :--- | :--- | :--- |
| **ActiveProbe:**<br>`LOOP CONFIRMED` | **Closed Physical Loop.** | **IMMEDIATE ACTION**<br>The alert now includes the `CONNECTED TO` field. **Go directly to that indicated switch and port** and disconnect the cable. No need to manually trace cables. |
| **FlapGuard:**<br>`MAC FLAPPING` | **Topology Instability.**<br>A cable bridging two VLANs or Native VLAN error. | **INVESTIGATE CABLING**<br>1. Trace the MAC to see between which ports it jumps.<br>2. Verify "Native VLAN" on Trunks. |
| **ArpWatchdog:**<br>`ARP STORM` | **Control Plane Storm.**<br>Early symptom of loop or massive scan. | **CORRELATE**<br>1. If it appears with *EtherFuse*, it's a loop.<br>2. If it appears alone, it's an infected host: locate and isolate it. |
| **DhcpHunter:**<br>`ROGUE DHCP` | **Home router connected.**<br>Someone connected a TP-Link/D-Link router through the LAN port. | **IMMEDIATE BLOCK**<br>The reported MAC is the intruder router's port. Block that port on the switch or use *BPDU Guard*. |
| **FlowPanic:**<br>`PAUSE FLOOD` | **Hardware Failure / DoS.**<br>Dying NIC or L2-level denial of service attack. | **REPLACEMENT**<br>The source device is defective. Disconnect it before it freezes the entire switch. |
| **RaGuard:**<br>`ROGUE IPV6 RA` | **IPv6 MITM.**<br>A misconfigured PC or attacker announcing itself as IPv6 Gateway. | **SECURITY**<br>Investigate the source MAC. It could be an attempt to intercept traffic through IPv6 autoconfiguration. |
| **McastPolicer:**<br>`MULTICAST STORM` | **Multicast Storm.**<br>Cloning software, IPTV, or IP cameras out of control. | **INVESTIGATE SOURCE**<br>Identify the multicast source. Could be misconfigured FOG/Clonezilla or a loop amplifying multicast. |
| **BcastRatio:**<br>`HIGH BROADCAST RATIO` | **Network degradation.**<br>Broadcast percentage exceeds configured threshold. | **MONITOR**<br>Early warning. If it exceeds 80%, the network is on the brink of collapse. Correlate with EtherFuse/ActiveProbe. |
| **VlanLeak:**<br>`VLAN LEAKAGE` | **Segmentation leak.**<br>Traffic crossing between VLANs that should be isolated. | **IMMEDIATE AUDIT**<br>Review trunk and access port configuration. Possible segmentation policy violation (PCI-DSS). |
| **MetaEngine:**<br>`CONFIRMED LOOP` | **Loop confirmed with high confidence.**<br>Multiple independent engines have fired simultaneously. | **IMMEDIATE ACTION**<br>This is near-certainty. Follow the `CONNECTED TO` indications and disconnect the problematic cable. |
| **ArpWatchdog:**<br>`GRATUITOUS ARP FLOOD` | **IP conflict or ARP attack.**<br>GARP packet flooding from a host. | **INVESTIGATE**<br>Could be VRRP/HSRP flapping, duplicate IP conflict, or an active ARP Poisoning attack. |

## 🛠️ Installation and Usage

LoopWarden is designed to be compiled and run directly from its source code on Linux environments. Go 1.25+ and `make` are required for the compilation process.

### Secure Compilation and Execution

```bash
# Step 1: Clone the LoopWarden repository
# Gets the latest version of the source code.
git clone https://github.com/soyunomas/LoopWarden.git
cd LoopWarden

# Step 2: Download dependencies and compile the optimized binary
# 'make deps' syncs Go modules.
# 'make build' compiles the executable, optimizing for production (strip symbols, no debug info).
make deps
make build

# The resulting binary will be in the ./bin/loopwarden directory

# Step 3: Assign Network Capabilities (Recommended for Security)
# Instead of running as full 'root', only the necessary permissions
# to open raw sockets ('CAP_NET_RAW') are granted. This improves security posture.
sudo setcap cap_net_raw=+ep ./bin/loopwarden

# Step 4: Run LoopWarden
# The binary can now be executed by a non-root user, reading the configuration.
# Make sure to adjust 'configs/config.toml' according to your environment.
./bin/loopwarden -config configs/config.toml
```

### Deployment as System Service (systemd)

For continuous and robust production operation, deploying LoopWarden as a `systemd` service is recommended.

```bash
# Step 1: Copy the binary to a standard system location
sudo cp bin/loopwarden /usr/local/bin/

# Step 2: Create the service configuration directory
sudo mkdir -p /etc/loopwarden

# Step 3: Copy the configuration file to the service directory
sudo cp configs/config.toml /etc/loopwarden/

# Step 4: Install the systemd unit file
# This allows systemd to manage LoopWarden's start, restart, and monitoring.
sudo cp deploy/systemd/loopwarden.service /etc/systemd/system/

# Step 5: Reload systemd, enable and start the service
# 'daemon-reload' updates systemd with the new unit.
# 'enable --now' enables the service to start at boot and starts it immediately.
sudo systemctl daemon-reload
sudo systemctl enable --now loopwarden
```

### Cross-Compilation (Raspberry Pi and OpenWRT)

LoopWarden supports cross-compilation for multiple embedded platforms:


### High Performance Tuning (>10Gbps)

For high-speed network interfaces (10Gbps or higher) in high-load environments (e.g., Core Routers, DMZ) or under massive attacks, optimizing the Kernel's network subsystem is essential to avoid packet loss.

1.  **NIC Ring Buffer Adjustment:**
    *   **Command:** `ethtool -G <interface_name> rx <buffer_size>`
    *   **Example:** `sudo ethtool -G eno1 rx 4096`
    *   **Description:** Increases the size of the memory "ring" (Ring Buffer) that the network card uses to store packets before the Kernel processes them. A larger buffer reduces packet drops (`rx_dropped`) under traffic spikes. The optimal value is specific to each NIC and its driver.

2.  **Kernel Socket Buffer Adjustment:**
    *   **Commands:**
        *   `sudo sysctl -w net.core.rmem_max=26214400`
        *   `sudo sysctl -w net.core.rmem_default=26214400`
    *   **Description:** `rmem_max` and `rmem_default` control the maximum and default receive buffer size for all Kernel sockets. Higher values (here 25MB) allow LoopWarden's raw sockets to accumulate more data in the Kernel before the Go application needs to read them, reducing processor overload risk and ensuring complete capture even under severe storms. To make them permanent, add to `/etc/sysctl.conf`.

> **Why LoopWarden if I already have STP?**
> Spanning Tree (STP/RSTP) is slow to converge and often fails on "Edge Ports" where users connect unmanaged switches or make cabling mistakes. LoopWarden detects loops, storms, and topology anomalies in **milliseconds**, providing the telemetry that switches lack.

## 🏗️ "Fast-Path" Architecture

LoopWarden is designed to process traffic at line speed without drowning the CPU, using a **Parallel Stacks (Shared-Nothing)** architecture to manage multiple interfaces without lock contention:

```text
[ NETWORK WIRE ] <=== (Multiple Interfaces: eno1, eno2...)
      ||
[ NIC HARDWARE ]
      ||
[ KERNEL RING ] <--- (AF_PACKET RX_RING per Interface)
      ||
[ BPF FILTER ]  <--- "Drop Unicast. Keep Broadcast/Multicast/ARP/Tagged/Control"
      ||
[ GO RUNTIME ]  <--- (Parallel Stacks)
      ||
      +--> [ Engine Stack 1 (eno1) ]
      |      ||
      |      +-- 1. ActiveProbe (Identity Injection: "Magic|eno1")
      |      +-- 2. EtherFuse (Local State & Overrides)
      |      +-- ... (All Engines)
      |
      +--> [ Engine Stack 2 (eno2) ]
             ||
             +-- 1. ActiveProbe (Identity Injection: "Magic|eno2")
             +-- 2. EtherFuse (Local State & Overrides)
             +-- ... (All Engines)
             ||
[ NOTIFIER ] <-- (Centralized Deduplication & Throttling)
      ||
[ ALERTS ] ----> Slack / Syslog / Email (Tagged with [SensorName])
```

> **⚠️ Technical Note on Performance (Kernel BPF):**
> LoopWarden uses Kernel-Space BPF Filters (cBPF JIT). This discards irrelevant Unicast traffic before it crosses the User-Space boundary, avoiding costly context switches and ensuring line-speed processing without saturating the CPU.
